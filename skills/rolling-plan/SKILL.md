# Rolling Plan（滾動式 PLAN.md）

## 這個 skill 在解決什麼

一個 agent 或系統剛起步時，遠處的事情幾乎都看不清楚：要測過才知道的、要等前一段做完才知道形狀的、需要再查資料的。這時候硬把整條路寫細，只會得到一份很快就過期、大家也不再相信的計畫。

所以 PLAN.md 只做三件事：**講清楚終點、把下一步寫到能動手、把每次轉彎記下來**。遠的 phase 留白不是偷懶，是誠實。

它在開發流裡的位置：`survey-mode`（倒料）→ **`rolling-plan`（收斂成計畫）** → `repo-init-adopt`（讓 repo 長成固定形狀）→ `cip-loop`（邊用邊改）。

## 什麼時候用

- survey 收斂之後，第一次寫 PLAN.md
- 一個 phase 達成完成條件，要開下一個 phase 之前
- 某條 CIP 動到了方向、phase 順序或完成條件

## 原則

1. **以終為始。** 第一段寫終點：做完之後，誰的工作會變成什麼樣子。不是功能清單，是那個人的日常變化。
2. **近細遠粗。** 只有下一個 phase 寫到能動手；後面的 phase 各一兩句方向。遠處缺 context 很正常，等前一個 phase 做完再補。
3. **每個 phase 都有完成條件，寫成可以檢查的句子。** 「功能做完」不算；「實際用了兩週、沒有回頭用舊方法」算。
4. **每個 phase 的起手式是它自己的 survey。** 開工前先倒一輪這個 phase 的需求、現況、資料來源，不沿用整個專案最早那次 survey。
5. **不寫日期，除非 owner 明確要求。** phase 只寫順序與完成條件。日期一寫上去就會變成承諾，而遠的 phase 本來就看不清。
6. **要測過才知道的，寫成「待 phase N 驗證」**，不要先猜答案。

## PLAN.md 結構

```markdown
# PLAN

## 終點
（一段話：做完之後，誰的工作會變成什麼樣子）

## 現況
- 目前在：Phase N
- 最後更新：YYYY-MM-DD

## Phases

### Phase N：（名稱）← 目前
- 目標：
- 前置準備：（含這個 phase 的 survey、要先查的、要先備好的）
- 主要工作：
- 完成條件：（可檢查的句子）

### Phase N+1：（名稱）
- 方向：（一兩句）

### Phase N+2：（名稱）
- 方向：（一兩句）

## 決策紀錄
| 日期 | 決定 | 理由 | 觸發來源 |
|---|---|---|---|
| YYYY-MM-DD | | | survey / CIP 名稱 |
```

## 步驟

1. 讀 survey 的收斂結果，以及現有的 PLAN.md（如果有）。
2. 寫或更新「終點」。**終點有變，先跟 owner 確認再往下寫。**
3. 只把下一個 phase 寫細：目標、前置準備、主要工作、完成條件。
4. 後面的 phase 各留一兩句方向。
5. 這次的取捨寫進決策紀錄，標明是哪次 survey 或哪條 CIP 觸發的。
6. 更新「現況」。

## 紅線

- **不把遠的 phase 假裝寫細。** 寫得越細，過期得越快，也越容易被誤當成承諾。
- **不自己改終點。** 終點是 owner 的決定；你可以指出「這次 survey 好像跟終點有張力」，但改不改由 owner 說。
- **不把日常改進塞進 PLAN.md。** 小改進屬於 CIP.md（見 `cip-loop`）。PLAN.md 只記會動到方向、順序、完成條件的事。

## 完成檢查

- [ ] 終點一段話講得清楚，讀的人知道做完會怎樣
- [ ] 下一個 phase 有前置準備與可檢查的完成條件
- [ ] 遠的 phase 沒有假裝很細
- [ ] 決策紀錄有這次的變動、理由與觸發來源
- [ ] 現況寫明目前在哪個 phase
